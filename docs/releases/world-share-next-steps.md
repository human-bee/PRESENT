# Smallest remaining steps to a public release

The seven stacked PRs deliver tested software. They are draft release candidates; local branches, screenshots and private backups are not deployed truth. P0 through P4 cloud checks are green at the sprint checkpoint. Read P5/P6 exact-commit cloud status before promotion.

1. Review the seven phase diffs in order and select the final release commit. Merge through the established main deployment path only after release authorization.
2. Obtain a legitimate tldraw license covering the actual public domain. Configure the build-time license for that domain and rebuild. A present environment variable or localhost editor is not proof of license validity.
3. Deploy the selected revision to an isolated signed staging service with one durable writer. Read health revision and actual browser license/editor state from that host.
4. Choose the public executor boundary. The inspected hosted container does not currently contain an authenticated Codex workspace executor. Keep planning-only behavior honest until the chosen executor proves actual commands/files on that host. Do not treat an API planning key as workspace execution.
5. Before exposing paid execution beyond the operator, define and enforce admission, per-user/room concurrency and cumulative paid-turn limits. The private two-turn proof fence is not a public quota system. Verify anonymous session and new-room paths against the chosen access policy, not only invite revocation in existing rooms.
6. Test one real owner/editor/viewer room on that host: invite, correction, reconnect, artifact, Stop, reload and revoked-access rejection. Preserve exact host/commit/model/turn receipts. Physical-device or pilot-team logistics are not gates for this sole-user sprint.
7. Take an encrypted stopped-service backup and perform a restore into a new isolated root before promotion. Retain the access signing secret and executor configuration separately, with the tested single-writer topology.
8. Promote the exact accepted revision through main. Recheck production health revision, domain license, signed-room access and the selected executor capability. Then share the verified entry point.
9. Run one real planning/review session, capture an operator judgment of usefulness and trust, and record an actual return. Participant Done and scripted reload counts remain observations rather than evidence of completed work or retention.

Project follow-through currently supports bounded text additions/edits and explicit per-file apply. Whole-repository atomic apply, deletion/binary/executable changes, interrupted-apply reconciliation, multi-host locking, real WAN latency, full power-loss testing and broader product validation remain separate development work. The151-chat audit and101-step roadmap remain the detailed source plan in the original project reports.
